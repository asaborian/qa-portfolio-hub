# QA Portfolio Hub

> **💡 本リポジトリの目的**
> 
> 本リポジトリは、採用担当者様の参考資料として、私のQAエンジニア転職に向けた技術習得状況や、面接での想定質問に対する回答等を、事前にドキュメントとして公開しているものです。目的は以下の2点です。
> 
> 1. **意思と前提条件の正確な伝達**
>    面接当日の限られた時間やその場のやりとりだけでは、自身のキャリアに対する考え方や、想定している勤務条件を100%正確に伝えることは困難です。事前にテキストとして可視化しておくことで、認識の齟齬をなくすことを目的としています。
> 
> 2. **採用活動におけるミスマッチ防止**
>    私の現在のスキルセットや、育児との両立を目指した希望勤務条件（猶予期間を設けた上での原則リモートワーク等）をあらかじめ開示しております。企業様が求める人物像や要件と照らし合わせて選考の初期段階でご判断いただくことで不要な面接の発生を防ぎ、私よりも優秀な人材を求める企業様・採用担当者様に対して、選考の手間をおかけしないようにすることを目的としています。

## 📝 Recent Learning Logs

- **2026-08-14 17:43**: 「高カバレッジ＝高品質」とは限らない理由とQA視点での注意点：カバレッジは単に「存在するコードのうち実行された割合」を示す指標に過ぎず、「仕様通りに動作しているか」や「本来書かれるべき処理の欠落（考慮漏れ・例外ハンドリング不足など）」を検知することはできない。また、数値目標（100%など）を形骸化させて課すと、`test("表示テスト", () => { render(<Header />); });` のようにアサーション（検証）を行わずにただコンポーネントを実行して通過させるだけの「無意味なカバレッジ稼ぎテスト」が横行するリスクがある。カバレッジの数値向上を目的化させず、検証の質（意味のあるテストケースと適切な検証ルール）を保つことが本質的である。
- **2026-08-14 17:42**: 「高カバレッジ＝高品質」とは限らない理由とQA視点での注意点：カバレッジは単に「存在するコードのうち実行された割合」を示す指標に過ぎず、「仕様通りに動作しているか」や「本来書かれるべき処理の欠落（考慮漏れ・例外ハンドリング不足など）」を検知することはできない。また、数値目標（100%など）を形骸化させて課すと、 のようにアサーション（検証）を行わずにただコンポーネントを実行して通過させるだけの「無意味なカバレッジ稼ぎテスト」が横行するリスクがある。カバレッジの数値向上を目的化させず、検証の質（意味のあるテストケースと適切な検証ルール）を保つことが本質的である。
- **2026-08-14 17:37**: Vitest等のツールを用いて実行されたコードの割合を客観的・数値的に計測できるコードカバレッジ（コード網羅率）の定義とテスト戦略: カバレッジは主に単体テストレベルで計測されE2Eテストとは別物である。指標にはC0（命令網羅：全行実行）、C1（分岐網羅：if文等の真偽分岐実行）、C2（条件網羅：個々の条件式の組み合わせ実行）などの種類がある。ツールで客観的な計測が可能であるものの、全領域で100%を目指すのではなく、重要分野であるドメインロジック（料金計算や権限チェック等）は90〜100%の高カバレッジを目指す一方、画面UIなど変更頻度が高い領域ではあえて目標値を低く設定（または0%）にする。これは仕様変更時のテスト修正（メンテナンス）の手間を減らすためのトレードオフであり、UI領域などはE2Eテストで補完するテスト設計が妥当である。
- **2026-08-14 17:15**: FMEA（Failure Mode and Effects Analysis：故障モード影響解析）とFTA（Fault Tree Analysis：故障木解析）の定義およびテスト設計への適用。FMEAはボトムアップ型（構成要素の故障から影響を推論）でモジュール単位・単体テストレベルの異常系網羅に活用。FTAはトップダウン型（システム全体の致命的障害から原因を木構造で分析）で結合・E2Eテストを含む全体のテスト戦略やシナリオ設計の根拠となる。
- **2026-08-13 11:47**: DDDにおける主要概念の定義。エンティティは識別子（ID）により同一性が識別され、属性値が変化しても同一の存在として扱われるオブジェクト。値オブジェクトは識別子を持たず、値そのものの同一性で判断される不変なオブジェクトであり、自身のバリデーションルール等を内包する。コンテキストマップは、境界づけられたコンテキスト間におけるデータの流れる方向や連携関係を可視化した構造図。

## 💬 Interview FAQ

### Q: 就職したらどのように貢献できるか？
A: セキュリティスペシャリスト(SC)の知識を活かし、JSTQBの標準的なテスト技法に基づいて、Playwrightを活用したテスト自動化を構築できます。

### Q: なぜ37歳実務未経験でITエンジニアを目指すに至ったのか？
A: 現職の業務効率化のためにExcelマクロを使うようになり、プログラミングが楽しいと感じて仕事にしたいと考えたのが始まりです。当初は、「いつか個人開発や案件で生計を立てられたらいいな」という程度の考えで、転職時期については深く考えずに、趣味レベルで独学を続けていました。しかし、子どもが生まれたことをきっかけに、育休終了後の生活について夫婦で話し合った結果、「リモートワークができる企業への転職」が最適であるという結論に至りました。そこで、自分に合いそうな職種として、セキュリティに強いQAエンジニアというポジションを目指すことにしました。

### Q: 具体的にどのような勤務形態を想定しているか？
A: フルフレックスの原則リモートワークを想定していますが、採用後最初の3ヶ月間を上限として、職場のルールや基本業務をキャッチアップするための期間であれば、出社可能です。それ以降は、子どもの幼稚園の送り迎えのため、原則リモートワークの勤務形態へ移行する必要があります。なお、リモート移行後も、月1回程度の頻度や、事前に調整ができるスケジュールであれば、家族と調整のうえ出社可能です。リモート移行後の普段の働き方としては、例えば、次のような形であれば可能です。

* **5:00 ~ 7:00 2時間勤務**
  (8:30前後に幼稚園送迎)
* **9:00 ~ 13:00 4時間勤務**
  (14:00前後に幼稚園送迎)
* **20:00 ~ 22:00 2時間勤務**
* **合計: 8時間勤務**

なお、14時から20時頃は子どもが家にいるため、業務に専念する時間（勤務時間）にはカウントできないものと考えております。ただし、その時間帯もスマートフォン等での急ぎのご連絡には随時対応可能ですので、チームの業務進行に支障が出ないよう配慮します。子育ての都合で毎日決まって同じ時間に働くことは難しいかもしれませんが、状況に応じて妻や実家のサポートを受けながら、月の総労働時間をしっかりと確保いたします。

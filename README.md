## 📝 Recent Learning Logs

- **2026-10-05 23:14**: データベース（RDB）におけるWAL（Write-Ahead Logging）、バッファキャッシュ、データファイルの相互作用と同期メカニズム： 1. データ更新とログ先行書き込み（WAL）： データ更新時、DBはメモリ上のバッファキャッシュ（ページ）を直接書き換え、同時に変更差分ログ（WAL）をディスクへシーケンシャルI/Oで追記する。データファイル本体へのランダムI/Oは即座に行われず遅延される。 2. データファイルへの適用（Disk Write）： メモリからデータページが追い出されるタイミング（Eviction）や、定期的なチェックポイント（Checkpoint）において、ログを解析・解釈して適用するのではなく、メモリ上に存在する更新済みの最新ページデータがそのままデータファイルへ上書き（コピペ）される。 3. データの整合性保証： データページがバッファから破棄される直前に必ずディスクへ書き戻されるため、次にディスクからデータが読み込まれる時点では常に最新状態が維持される。 4. WALの本来の役割： WALログは通常時のSELECTやディスク適用処理では一切読み込まれず、クラッシュ等の異常発生時にメモリ上の最新状態を復元（REDO/UNDO）するためだけに読み込まれる。
- **2026-10-05 23:14**: サービスデスクの必要要員数は、時間ではなく「シフトの個数」ベースで計算する。まず「労働時間上限 ÷ 1シフト労働時間（切り捨て）」で1人あたりの上限シフト個数を算出する。次に「全シフトの合計個数 ÷ 1人あたり上限シフト個数（切り上げ）」で必要な要員数を求める。
- **2026-10-04 14:44**: TCP通信において、コネクション確立が3ウェイ・ハンドシェイクで行われるのに対し、切断処理が4ウェイ・ハンドシェイクとなるのは、双方のデータ送信完了タイミングが一致しないためである。接続時は相手からの要求への確認（ACK）と自身の接続要求（SYN）を1つのパケットにまとめて送受信できる（「了解」と「私も」を同時に伝える）ため3回で完了する。一方で切断時は、一方の送信完了要求（FIN）に対し受領応答（ACK）を即座に返したあとも、もう一方のホストに残りの送信データが存在する可能性があるため、自身の送信完了要求（FIN）を個別に送信する必要があり、合計4回のやり取りを要する。
- **2026-10-04 14:41**: TCP/IPの切断動作（4ウェイ・ハンドシェイク）において、最後にACKを送る側のホストは「自身のACKが相手に到達したか」を直接確認できない。これは通信工学における「二人の将軍問題」に起因し、不確実な通信路上で双方が完全に受信完了を合意し合うことは原理的に不可能であるためである。そのためTCPでは、最後のACK送信後に一定時間コネクションを維持するTIME-WAIT状態を設けることで、ACK不達時に再送されてくるFINへ対応する現実的な解決策をとっている。
- **2026-10-01 22:25**: Hadoopは単一の高性能なサーバーではなく、複数の一般的なコンピュータをネットワークで接続したクラスタ環境で動作するフレームワークである。Hadoopのソフトウェア群は中央だけに置くのではなく全ノードにインストールし、全体の指揮を執るマスターノードと、実際にデータの保持や計算を行う複数のワーカーノードとして役割分担させて稼働させる。分散ストレージ機能のHDFS（Hadoop Distributed File System）はデータをブロック単位に分割し、複数のノードへ複写（レプリケーション）して保持することで高い耐障害性を実現する。分散処理フレームワークのMapReduceは各ノードが局所的にデータを処理（Map）した後に集計（Reduce）を行い、これらの計算リソース管理およびジョブスケジューリングはYARNが統括する。

## 💬 Interview FAQ

### Q: 就職したらどのように貢献できるか？
A: セキュリティスペシャリスト(SC)の知識を活かし、JSTQBの標準的なテスト技法に基づいて、Playwrightを活用したテスト自動化を構築できます。

### Q: どのような企業形態・契約形態を希望しているか？
A: 育児（幼稚園の送迎等）と両立可能な環境であることを前提に、SaaS・SIer・QA専門企業といった事業形態や、正社員・業務委託等の契約形態にはこだわらず、広く機会を探しています。
私の理想とする働き方は、「時間あたりの単価に対する価値を最大化し、かつ長期的に安定して成果を出し続けられる形」です。1日4時間ほどで高密度に業務をこなし、業務時間外に技術インプットを行うスタイルが、長期的に安定して高いパフォーマンスを出し続けること（持続可能性）と、企業様にとっての投資対効果の高さを両立する最高の形と考えております。
ただし、フルタイムで求人を出している企業様に関しても、フルフレックス制度等で時間の調整が可能であり、業務に必要な技術調査や仕様把握等のキャッチアップ時間を勤務時間として扱える環境であれば、**フルタイム（1日8時間稼働）での参画**も喜んでお受けいたします。
具体的には、内定・契約時に以下の点が書面で確認・合意できることを前提としております。

1. **原則リモートワーク**
   * オンボーディングに伴う出社期間は入社後最大3ヶ月間とし、それ以降は原則リモートワークへ移行すること。
   * リモート移行後も月1回程度の出社や緊急時の対応は可能ですが、高頻度な定例出社（週1回・隔週等）がないこと。
2. **勤務時間の柔軟性**
   * 13:30以降はコアタイム等の拘束がないこと。早朝・午前・夜間等、育児中ではない時間帯で総労働時間を確保できること。

書面にて合意することで、入社後のミスマッチを防止したいと考えております。

### Q: なぜ37歳実務未経験でITエンジニアを目指すに至ったのか？
A: 現職の業務効率化のためにExcelマクロを使うようになり、プログラミングが楽しいと感じて仕事にしたいと考えたのが始まりです。当初は、「いつか個人開発や案件で生計を立てられたらいいな」という程度の考えで、転職時期については深く考えずに、趣味レベルで独学を続けていました。しかし、子どもが生まれたことをきっかけに、育休終了後の生活について夫婦で話し合った結果、「育児（幼稚園の送迎等）と両立できる仕事への転職」が最適であるという結論に至りました。そこで、もともとなりたいと思っていたITエンジニアへの挑戦を決め、自分に合いそうな職種として、セキュリティに強いQAエンジニアというポジションを目指すことにしました。
